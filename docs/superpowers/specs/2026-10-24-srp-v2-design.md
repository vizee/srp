# srp v2.0 设计草案

日期：2026-10-24。更新：2026-10-25。状态：设计讨论中；已确定动态监听管理协程模型，尚未实施。

## 目标与范围

用户明确要求 v2 完全重新开发，可按清空现有应用代码后重建的项目理解；不是在 v1 上重构或保留旧架构。提供 expose/relay 两种运行模式。expose 主动连接 relay，一个控制连接声明多个服务；relay 按服务名将不同监听地址上的 TCP 连接转发给对应 expose，并在多个 expose 之间轮询。

不读写运行配置文件；密钥文件是唯一必需的外部输入。建议继续使用 Go，优先使用标准库，但旧项目的 Go 1.20 下限、依赖策略、文件结构和内部 API 均不构成 v2 的约束；工具链与依赖在实施计划中按实际需要确定。支持 TCP、IPv4/IPv6、域名目标、并发请求、双向流式转发和 TCP 半关闭。

v2 不兼容旧命令和旧线协议，不迁移旧 link/agent、预读、待命数据连接池及相关参数。`-v` 调试日志仍有价值，可作为 v2 的独立设计保留；`systemd-service` 并非用户要求的核心功能，是否纳入 v2 待定，不能仅因旧版本存在就默认保留。

不加入 UDP、配置热更新、Web 管理界面、TLS 证书体系、流量复用、服务发现协议、按 expose 权重分流或数据连接自动迁移。

## 已选择的方案

最初讨论过两种握手方案：

1. AES-CTR 加密随机数据、握手数据及 CRC32，后续使用 AES-GCM。格式最小，但 CRC32 无法承担消息认证。
2. 在原始外层布局下，将 HMAC-SHA256 放入握手数据内部；再进行随机挑战和加密确认，后续使用 AES-GCM。增加少量握手内容与一次往返，能够认证消息，并避免旧握手直接触发注册或消费连接 ID。

用户已选择推荐的带认证方案，并允许继续讨论未定细节。后续用户要求 CRC/HMAC 二选一，实现方选择保留 HMAC-SHA256、删除 CRC32；当前首包仅进行 HMAC 消息认证，不叠加 CRC。以下具体字段、超时、错误策略和资源管理是实现方建议，除明确标记外尚待整份文档批准。

## 命令行

```sh
srp expose \
  -k /path/to/shared.key \
  -r 100.100.100.100:7770 \
  -t ssh=127.0.0.1:22,myweb=192.168.1.11:8080,egress.baidu=www.baidu.com:443

srp relay \
  -k /path/to/shared.key \
  -l :7770 \
  -s ssh=:8022,myweb=100.100.100.100:18080,egress.baidu=127.0.0.1:443
```

| 参数 | 模式 | 默认值/规则 |
| --- | --- | --- |
| `-k` | 两者 | `$HOME/.config/srp/default.key`，通过 `os.UserHomeDir` 定位；显式路径直接作为文件名 |
| `-r` | expose | `127.0.0.1:7770` |
| `-t` | expose | 必填，非空的 `服务名=目标地址` 列表 |
| `-l` | relay | `:7770`，同时接收控制连接与数据连接 |
| `-s` | relay | 必填，非空的 `服务名=监听地址` 列表 |
| `-v` | 全局 | 放在子命令前，保留现有形式 |

密钥文件包含原始的 16、24 或 32 字节高熵共享密钥，读取后不 trim、不做 Base64 解码。删除旧的 `@文件`/直接 Base64 参数语义；不会自动生成密钥，避免两端各自产生不同密钥。文件不存在或密钥长度不合法时启动失败，错误给出路径和原因，不输出密钥内容。文档提供 `umask 077; openssl rand -out ... 32` 的手动生成步骤。

映射列表按逗号切分，每项只在第一个 `=` 处分隔；去除每项及两侧首尾空白。拒绝空项、重名、空服务名、无效端口和尾随参数。服务名区分大小写，限制为 1–128 字节的 `[A-Za-z0-9._-]+`，支持 `egress.baidu`；每个 expose 最多声明 256 个服务。地址采用 Go `host:port` 语法，IPv6 使用 `[::1]:22`。目标必须有非空 host，端口范围为 1–65535；监听地址允许空 host，生产 CLI 不允许端口 0。监听不提前尝试 bind，格式检查不违反按需监听要求。

## 信任边界

共享同一密钥的 expose 属于同一个信任域，均有权注册 relay 配置中的服务。服务名用于路由，不是隔离不同租户的授权凭证。relay 永远不接收或下发实际目标地址；expose 只拨号自身 `-t` 中的目标。

认证加密覆盖 expose 与 relay 之间；客户端到 relay、expose 到目标沿用业务自身协议。此方案不提供前向保密：共享密钥泄露后，已录制流量可能被解密。这不是本次额外引入密钥交换体系的理由，但必须在文档中说明。

## 首包：单一 HMAC 校验

```text
IV[16] | AES-CTR(K_handshake_enc, IV,
    random[24] | handshake_data | hmac[32])

handshake_data = json_length[4] | json[json_length]
```

- AES block 固定 16 字节，因此 random 正好是 1.5 个 block，也就是 24 字节。
- IV 与 random 分别从 `crypto/rand` 独立生成。
- 所有新协议整数统一使用大端序。
- `json_length` 为 uint32，范围 1–65536；接收方先解密 random 与长度，再按上限读取剩余内容，不进行无界分配。
- HMAC 输入为 `IV || random || json_length || 原始 JSON 字节`，使用独立的握手认证密钥，接收方通过 `hmac.Equal` 比较。
- HMAC 为完整的 32 字节 HMAC-SHA256 结果，与 random、handshake_data 一起加密；首包不包含 CRC32。
- 接收顺序：有界读取、解密、校验 HMAC、解析与校验 JSON（包括客户端时间）、原子检查并记录 nonce，通过后才进入随机挑战。失败即关闭；未认证的错误不返回具体原因，仅可在本地调试日志记录。
- 不使用 CBC 填充，也不在 IV 前放明文长度或固定 magic。

控制连接 JSON 示例：

```json
{"version":2,"type":"control","timestamp_ms":1792857600000,"services":["ssh","myweb","egress.baidu"]}
```

数据连接 JSON 示例：

```json
{"version":2,"type":"data","timestamp_ms":1792857600000,"id":"32字节随机ID的小写十六进制表示"}
```

控制服务列表不得为空或重名，数据握手不得夹带服务列表。拒绝不支持的版本、未知类型及语义矛盾的字段。JSON 字段顺序不参与语义判断，HMAC 认证的是收到的原始字节，不依赖 JSON 重编码。

**用户新增要求：**控制和数据握手均携带客户端时间。建议字段为必填 int64 `timestamp_ms`，表示发送首包时的 Unix 毫秒时间；它位于加密 JSON 内，受 HMAC 覆盖。缺失、非整数或越界时拒绝；接收方验证 HMAC 后，按自身当前时间检查。

**用户已确定：**双向检查时间差；客户端领先或落后达到 10 秒均拒绝。有效窗口为 `server_time - 10s < client_time < server_time + 10s`，恰好 10 秒也拒绝。服务端在完成首包认证后读取当前时间检查，时间戳不合法时不进入服务注册或数据 ID 认领。

**用户已确定：**relay 在内存中维护全局 nonce 表，nonce 就是握手中的 24 字节 random 部分，不按 expose 或连接分表。同一个 nonce 自首次通过首包校验并成功登记起固定保留 **20 秒**，存活期间任何 expose 或连接重复使用都立即拒绝。查重与插入必须原子完成，控制与数据握手共用该表；只有通过 HMAC、时间和字段校验的首包才能占用表项。后续握手失败或连接关闭不提前删除该记录。

20 秒保留期覆盖完整时间窗口：若首包到达时客户端领先接近 10 秒，它仍可能在随后接近 20 秒内满足时间检查；收到后只保留 10 秒会过早忘记 nonce。举例：服务端时间 100 秒、客户端时间 109 秒，首包有效；到服务端时间 111 秒，10 秒缓存已过期而时间差只有 2 秒，旧消息仍有效；保留到服务端时间 120 秒后，原时间戳已失效。

nonce 表是 relay 进程级防重放状态，不能随某个 TCP/控制连接关闭而销毁或重建，否则重连会绕过查重。全局查重不依赖 expose 身份、当前 socket 或来源 IP，也不需要额外引入 instance_id/generation 字段。缓存应有容量上限，到达上限时拒绝新握手，不能提前驱逐仍有效的表项来接纳新握手。

时间窗口与 nonce 表补充既有认证流程；保留随机挑战、加密确认与 ID 原子一次认领，不因本次新增要求擅自删除。时间或 nonce 检查失败不得注册服务或消费数据 ID。nonce 表只在内存中维护，relay 重启后为空；既有随机挑战继续阻止单凭录制首包建立有效会话。

## 密钥派生与相互认证

采用 RFC 5869 的 HKDF-SHA256，使用 RFC 测试向量验证。具体使用工具链的现成实现还是标准库基础组件实现，随工具链选择确定，不为迁就旧版 Go 提前决定自行实现。

1. `root = HKDF-Extract(salt="srp/v2", IKM=共享密钥)`。
2. 从 root 以不同 info 标签派生 32 字节 `K_handshake_enc` 和 `K_handshake_mac`；标签分别为 `srp/v2/handshake/enc` 与 `srp/v2/handshake/mac`。
3. relay 验证首包后生成 32 字节随机 `server_nonce`，首先直接写入这 32 字节。它本身不是认证凭证。
4. `transcript = SHA256(完整首包线字节 || server_nonce)`；`session_root = HKDF-Extract(salt=transcript, IKM=root)`。
5. 从 session_root 分别按 `srp/v2/expose-to-relay` 与 `srp/v2/relay-to-expose` 派生两个 AES-256-GCM 密钥。
6. relay 用 relay→expose 方向发送加密 `challenge` 消息；expose 必须验证成功，再用 expose→relay 方向发送加密 `confirm`。
7. relay 验证 confirm 后，才执行服务注册或原子认领 pending ID；成功后发送加密 `ready`，失败可发送加密 `error` 后关闭。

随机挑战机制本身不依赖时钟或持久化状态；时间戳检查另外要求两端时钟满足约定偏差，nonce 表额外保存 20 秒内已校验首包的随机数据。即使录制首包因 relay 重启丢失缓存而通过首包检查，旧 confirm 仍无法通过本次新 session 的认证，因此不能单凭重放旧握手占用服务注册或消费 pending ID。

challenge、confirm、ready 与后续控制/业务数据持续使用同一个加密连接对象，序号不中途清零。接收代码不得通过带预读的 JSON decoder 越过 ready 边界读取业务数据。

## AES-GCM 流记录与消息

全新实现 v2 的认证加密流，定义有界记录、并发读写、短写处理、认证 EOF 与半关闭语义。旧 encryptedConn 不作为实现基础，v1 的派生方式、方向标签、接口和线格式均不继承。

```text
record = ciphertext_length[4] | ciphertext_and_tag[ciphertext_length]
nonce  = zero[4] | sequence[8]
AAD    = ciphertext_length[4]
```

每方向独立使用 uint64 序号，从 0 开始；每方向密钥最多使用 2^32 个记录，达到上限关闭连接，绝不重复 nonce。一个记录最多 32 KiB 明文，tag 16 字节；长度字段大端。认证失败、超长、截断、重排、重复或未收到认证 EOF 时直接失败，错误后不恢复继续读取。

握手确认和控制消息采用 `message_length[4] | JSON`，整体经过加密记录传输；JSON 长度 1–65536，使用 `io.ReadFull` 精确取数。业务连接 ready 后不再解析 JSON，直接使用 encryptedConn 传送原始 TCP 字节；任意字节值均合法。认证 EOF 保持半关闭：一端发送结束后仍能接收另一方向的数据。

控制消息最少包括：`heartbeat`、`open {id, service}`、`open_error {id, code}`。不增加 `cancel` 消息。ready 对控制连接返回 `accepted` 和 `ignored` 服务名列表，对数据连接确认认领成功。accepted 仅表示注册成功，不表示 relay 已成功开启对应监听；监听失败不能将服务归入 ignored。错误 code 使用固定枚举，不能携带目标地址或敏感内容。

## 控制连接与心跳

expose 一次只维护一个到指定 relay 的控制连接；每次重新连接均生成独立的首包和会话，relay 按独立控制会话注册。旧控制会话所属的待配对请求和数据连接不会迁移到新控制会话。不为 nonce 查重引入进程级 instance_id/generation；旧控制会话通过 EOF、错误或 7 秒心跳超时注销。

从 ready 完成后开始，双方每 5 秒发送一次 heartbeat。双方分别以最后一个完整且认证成功的 heartbeat 为基准设置 7 秒读取超时；业务请求或其他消息不代替心跳。初始基准为 ready 完成时间。失败的写入也关闭该控制连接。写操作最长 1 秒，保证被阻塞的控制写不会无限延迟心跳。

控制写入由专用协程串行处理，心跳不与后端拨号共享执行路径。open 投递队列有界，拥塞时关闭对应新客户端请求并记录可见原因，不阻塞全局注册锁。expose 读取 open 后异步处理拨号，不在控制读循环中等待 TCP 或数据握手。

expose 控制断开后重连，使用约 1、2、4、8、最高 10 秒退避并加入少量抖动；稳定连接至少 30 秒后重置退避，避免错误配置快速连接/断开刷屏。首次连接失败及状态变化输出正常日志；重复错误限频，逐连接细节留给 `-v`。

## 按服务注册与监听生命周期

relay 启动时只监听 `-l` 隧道入口。`-s` 仅创建服务定义，不 bind 服务端口。

控制握手双向认证完成后：

1. 将 expose 声明的名称与 `-s` 求交集。未配置名称列入 ignored，双方日志明确报告，不会按未配置名称自行创建监听；交集为空则返回错误，不建立有效注册。
2. 将 expose 加入所有匹配服务的成员列表，服务注册与监听是否成功分开处理。成员从零变为非零时通知该服务的监听管理协程开始监听；已有成员的服务不重复创建管理协程或 listener。
3. **用户已确定：**某个服务监听失败不影响本次注册成功，不回滚其他服务，也不要求 expose 重连或重新注册。relay 对失败服务记录警告日志并持续重试；其他已成功监听的服务继续接收请求。即使本次所有匹配服务的监听均失败，服务注册仍然成功，控制连接和心跳继续维持。
4. 注册完成即可返回 ready，不等待所有 listener 成功。接受请求的窗口必须确保 ready 先于 open 发送。ready 写失败属于控制连接失败，仍需注销本次成员；这与服务监听失败的处理不同。

注销发生于 heartbeat 超时、控制 EOF、协议错误、写失败或进程关闭。注销是幂等操作：删除该控制会话在所有服务中的成员资格，释放其所有未配对请求，并关闭其已配对数据会话；某服务成员数降到零时通知监听管理协程停止监听并取消重试。其他 expose 的注册、请求和数据会话不受影响。

监听管理状态由本服务的管理协程独占，不与服务注册表或轮询队列共用可变字段。accept 通过本轮 stopped 标记识别主动停止，调度使用服务当前有效的成员。注册表与轮询队列若存在跨协程访问，单独处理其同步；不为监听管理的局部变量增加锁。

### 每服务监听管理协程

**用户已确定：**每个已配置服务有且仅有一个长期运行的监听管理协程，执行 `select { case event := <-svc.event: ...; case <-tick: ... }`。listener 创建、当前 listener 指针替换、主动关闭及 ticker 启停都在这个协程内串行执行。它不直接承担 accept 或业务转发。

**用户明确：**`currListener net.Listener`、`stopped *atomic.Bool`、`ticker *time.Ticker`、`tick <-chan time.Time` 均为监听管理协程函数内的局部变量，只由该协程访问和修改，不放入可被其他协程读写的共享状态，也不需要 mutex。初始全部为 nil；nil tick 禁用定时分支，因此初始只等待 svc.event，不创建端口监听或无用 ticker。进程退出时通过 runtime 的退出信号清理这些资源并结束协程。

调用 `go accept(ln, stopped)` 时，将本轮 listener 接口值和 stopped 指针作为参数传入；accept 函数内持有自己的参数变量，不访问管理协程的局部变量。跨协程通信的是本轮 stopped 指向的 `atomic.Bool`：管理协程 Store，accept Load。将管理协程的 stopped 局部变量置 nil，并不会改变已传给 accept 的指针。

| 输入/结果 | 管理协程行为 |
| --- | --- |
| 开始监听事件 | 若已有 currListener 则幂等返回；否则立即尝试创建配置地址对应的 listener |
| 创建成功 | `currListener = ln`；为本轮 listener 新建独立的 `atomic.Bool`（初始 false）；`go accept(ln, stopped)`；若 ticker 存在则 Stop，并将 ticker、tick 均设为 nil |
| 创建失败 | 记录警告日志；若 ticker 为 nil，创建固定间隔 1 秒的 ticker 并令 tick 指向 ticker.C；否则继续使用原 ticker，不重建或叠加 ticker |
| tick 到达 | 在仍需要监听且 currListener 为 nil 时再次尝试创建；成功/失败沿用上述处理 |
| 停止监听事件 | 若 currListener 非 nil，先 `stopped.Store(true)`，清空管理协程的 stopped 指针，关闭并清空 currListener；若 ticker 非 nil 则 Stop 并清空 ticker、tick；重复停止是幂等操作 |

“停止”也适用于仅在重试、尚无 listener 的状态：不能因为 currListener 为 nil 而遗漏 ticker 清理。成功或停止后 tick 必须重新设为 nil，不让管理协程继续依赖已停用的 ticker 通道。

### accept 与事件处理约束

- 主动关闭前设置本轮 stopped；Accept 因关闭返回时，看到本轮标记为 true 即正常结束，不当成新的监听失败，也不自行重建 listener。
- 每次 Accept 返回一个连接后也检查本轮 stopped；属于已停止 listener 的连接直接关闭，调度时另行检查当前有效成员。
- 开始/停止事件要保持服务注册状态变更的顺序，或者将事件作为唤醒信号、由管理协程读取最新的期望状态；不能无条件丢弃事件导致最后一个成员退出后仍然监听，或已有成员却永久停止。具体投递实现由实施者确定。
- 对于非主动关闭引起的 Accept 异常，建议通过 svc.event 上报携带本轮 listener 身份的内部事件，由管理协程处理；accept 不访问管理协程的任何局部变量。具体错误分类仍可在实现时决定。
- 每个服务独立重试；一个服务 bind 失败不影响其他服务、控制心跳、服务注册成功或成员轮询。重复失败的警告日志可限频，但每秒重试周期不改变。

## 轮询与数据连接配对

每个服务有独立的有序成员队列。新成员追加到队尾；每次选择队首并将其移至队尾；移除成员不改变其余成员顺序。这给出按用户连接次数轮询的语义，不按并发连接数或流量计权。

收到客户端连接后：

1. 检查本轮 listener 的 stopped 标记，从该服务成员队列选择一个当前有效的控制实例；成员队列同步独立于监听管理局部状态。
2. relay 使用 `crypto/rand` 生成 32 字节 ID（64 个小写十六进制字符）；在发送 open 前创建 pending，保存服务、所选控制实例、客户端连接和 15 秒到期时间。
3. 通过所选控制连接发送 `open`，只含 ID 和服务名。发送失败时注销失效控制并关闭本次客户端；不把同一客户端请求自动分派给另一个 expose。
4. expose 校验服务属于自己的配置且 accepted，先以最多 5 秒连接目标，再建立到 relay 的独立 TCP 数据连接，发送携带 ID 的首包并完成双向认证。整个 open 处理使用 10 秒总预算，各拨号和握手受剩余预算约束。relay 不重复下发同一 ID。**用户明确修正：**到 relay 的 TCP 连接建立失败可以在本次请求预算内重试；完整首包发送成功后，该 ID 不再重试，即使随后时间校验/挑战/确认失败、被拒绝或连接关闭。首包写出发生错误但未明确成功的重试细节尚待确定，不能把“发送成功后不重试”误写为“TCP 拨号失败也不重试”。
5. relay 在 confirm 验证后原子检查 pending：尚未超时、控制仍有效、服务仍属于该实例且 ID 未使用。只有一个数据连接能成功认领，失败者关闭。
6. relay 发出 data ready，随后将客户端与加密数据连接双向转发；expose 收到 ready 后，将加密数据连接与目标 TCP 连接双向转发。

数据 ID 本身就是通过所属控制连接保密下发的一次性授权凭证。匹配时不依赖源 IP（允许 NAT），也不会仅凭数据握手自行声明一个服务就创建后端请求。同一共享密钥域中的节点本来就相互信任，不提供恶意持钥者之间的租户隔离。

目标拨号失败、数据连接在允许的建连重试预算内仍失败，或首包发送成功后握手失败时，expose 关闭已经打开的全部局部资源，并可在配对前尽力通过控制连接发送 open_error；relay 及时删除 pending、停止到期定时器并关闭客户端。无法报告时由 15 秒 pending 超时兜底。TCP 建连失败后决定继续重试时不提前发送 open_error 释放 ID；下一次允许的尝试使用新的随机 IV、随机数据和当前时间，不重放旧握手线字节。

**用户已确定：**ID 因等待超时、来源端关闭或其他原因提前释放后，relay 直接拒绝该 ID 对应的数据连接；不向 expose 增加 cancel 通知，也不恢复被释放的 ID。迟到连接、重复认领和未知 ID 均拒绝。同一 ID 的数据连接在握手后被关闭时，expose 认为本次数据链路结束，关闭对应目标连接并结束该数据任务，不重连、不重发握手，不退出 expose 的整个控制进程。

**用户已确定：**v2 支持 TCP 半关闭，包括配对尚未完成时来源端发送完请求并 CloseWrite、但仍等待响应的情况。单向 EOF 不释放 pending 或数据 ID；已接收的请求字节和该方向的 EOF 状态都需保留，配对后按原顺序转发，再关闭对端对应写方向，反向响应继续传输。

来源连接发生明确错误（例如 RST）或配对超时才按失败路径释放 pending；不能仅凭单向 EOF 推断对端已不需要响应。业务转发期间正常单向结束仅向对端传播半关闭，两个方向结束后释放整条会话；传输错误、控制会话关闭或进程退出仍立即关闭两端。这里不引入业务排空判断，也不把半关闭当作可重试的新会话。

pending 到期、来源端关闭、注销、认领和 open_error 必须通过同一原子状态转换竞争；以成功状态转换者为唯一连接所有者。每条客户端连接最终只有一个转发者或一个关闭路径，不得双重投递。认领只把请求从 pending 转为该控制会话所属的活动数据会话，不使它脱离控制会话生命周期。

## 中断与退出语义

**用户已确定：**不保留数据会话跨控制重连存续。控制会话关闭、心跳超时注销或被新的控制会话替换时，关闭该会话所属的所有待配对请求及已配对数据连接；expose 同时关闭对应目标连接，relay 关闭对应来源连接。新控制会话重新注册并只服务新的请求，不恢复、迁移或重试旧数据会话。

认领与控制注销在同一锁下竞争：认领先完成，则请求原子转为该控制会话的活动数据会话，随后注销仍会关闭它；注销先完成，则拒绝认领。不能在认领期间出现既不属于 pending、也不属于活动集合的清理盲区。ready 写失败时由数据处理者关闭两端并回收活动会话，ID 不回退、不重用。不能出现已注销后才接受新 ID 的窗口。

SIGINT/SIGTERM 或显式关闭 runtime 时，停止重连、拨号和心跳，关闭所有 listener、控制连接、pending 和活动数据连接，等待资源清理与协程退出。不增加“第一次信号排空、第二次强退”的机制，不尝试从通用 TCP 字节流推断业务何时排空。

## 超时、资源和运维

- 隧道 TCP 新连接至完成双向认证最多 5 秒，包括慢速/分片输入。
- 连接尝试、pending 及控制消息各自有 deadline，不对已建立业务连接保留握手 deadline。
- 所有写入使用完整写循环；短写、零进展或错误均进入明确清理路径。
- 采用有界的并发握手、pending 数量与控制 open 队列，达到上限拒绝新请求，不影响 heartbeat 和既有会话。具体容量留给实现者确定，并在 README 记录。
- 注册、注销、监听启停、端口冲突、后端连接失败、重连和正常退出输出简洁日志；调试日志可包含服务名/连接 ID，不能包含共享密钥、派生密钥或业务字节。
- 不根据探测流量发送 HTTP、TLS 或固定协议错误 banner。
- runtime 接口接收 context，明确协程、连接和取消信号的所有权，便于测试退出和资源清理。

5. 服务端口在首次有效注册前不监听；多 expose 加入时不重复 bind；最后注销后释放端口；重新加入能重建 listener。
6. 验证多个服务独立轮询、成员增删、未知服务反馈；监听失败时注册仍成功、其他服务继续可用、relay 警告并每秒重试，端口恢复可用后无须 expose 重连即可开始监听。验证初始 nil tick、重复开始不重建 listener、反复失败仅一个 ticker、成功后停 ticker 并置 nil、等待重试时停止也清理 ticker、重复停止、开始/停止快速交错及旧 accept 退出不影响新 listener。
7. 验证 5 秒 heartbeat/7 秒超时，目标拨号与大量 open 不阻塞 heartbeat；心跳中断注销并清理 pending 及所属活动数据会话。
8. 验证数据 ID 一次使用、超时/来源关闭后释放/重复/未知 ID、迟到连接、目标失败、并发 open_error/注销/认领及控制重连后的隔离；TCP 建连失败时允许重试，完整首包发送成功后不论认证失败、被拒绝或后续断开均不再重试该 ID，不因此终止其他任务或控制进程。
9. 抓取真实配对路径上的隧道字节，确认不存在业务明文；覆盖大流量、多个并发服务和服务端先发数据（例如 SSH banner）。
10. 端到端测试双向半关闭，特别是配对完成前来源端发送请求并 CloseWrite 时不释放 ID、请求完整送达且可接收完整响应；验证明确连接错误与配对超时的清理、控制断开关闭其全部所属数据会话、其他 expose 会话不受牵连、完整 runtime 退出后释放 listener 与连接且不等待业务排空。
11. `go test ./...`、`go test -race ./...`、`go vet ./...`、`go build` 和 `git diff --check` 通过；本地 TCP 测试在允许 loopback socket 的环境执行。
